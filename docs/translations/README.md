# Translations: updating languages and adding new ones

Localise.biz (Loco) is the **source of truth** for every translated string.
Everything under `assets/language/`, `assets/html/` and `ios/Runner/*.lproj/`
is generated from it. Editing those files by hand works until the next export,
which silently overwrites them.

This doc covers three things: how the pipeline is wired, how to refresh
existing languages, and the full checklist for adding a language that the app
has never shipped before.

---

## 1. What lives where

| Path | Contents | Generated by |
|---|---|---|
| `assets/language/<lang>_<REGION>.json` | Flat `key → string` map of all UI strings (~352 keys) | `update_locales.py` |
| `assets/html/{license,privacy,terms}_<lang>.html` | Full HTML legal pages | `update_locales_html.py` |
| `ios/Runner/<lang>-<REGION>.lproj/InfoPlist.strings` | iOS system permission prompts | `update_locales.py` |
| `ios/Runner/InfoPlist.strings` | Same, English base | `update_locales.py` |
| `lib/core/localizations/my_localizations.dart` | `supportedLocales` list | **hand-edited** |

Two things are worth internalizing because they cause most of the confusion:

**Translation *files* are not flavor-scoped, but language *availability* is.**
`assets/language/` is declared once in `pubspec.yaml` and ships in *both* the
`prod` and `dev` (Test Mosquito Alert) builds. What differs per flavor is the
offered-locale list: `MyLocalizations._betaLocales` (in
`lib/core/localizations/my_localizations.dart`) names languages that are still
under native-speaker review, and production builds exclude them from
`supportedLocales` — not in the Settings picker, and a device set to that
language falls back to English. The JSON still ships in the prod bundle,
merely unreachable. To promote a beta language to production, delete its
entry from `_betaLocales` (tests in `test/unit/beta_locales_test.dart` pin
this behavior). As of Sep 2026, Vietnamese (`vi_VN`) is the only beta locale.

**The runtime resolves a locale to a filename by string concatenation.**
`MyLocalizations._loadJsonAsset` builds `<languageCode>_<countryCode>.json`, or
just `<languageCode>.json` when the locale has no region. So the `Locale(...)`
entry in `supportedLocales` and the exported filename must agree exactly. A
mismatch is silent: `_loadJsonAsset` catches the failure and returns an empty
map, and every string falls back to English.

## 2. How the pipeline runs

### Automatically, on every git tag push

`.github/workflows/update_locales.yml` fires on any tag and does two jobs:

1. **`sync_tags_localise.yml`** — creates a Loco tag named after the git tag,
   then greps the codebase for in-use string keys and applies the tag to them:
   ```
   grep -hrPo "MyLocalizations\.of\s*\(\s*context\s*,\s*['\"]\K[^'\"]*" lib/
   ```
   This is why new strings **must** be written as a literal
   `MyLocalizations.of(context, 'my_key')`. A key built from a variable or
   split across lines is invisible to this grep, never gets tagged, and may not
   be exported.
2. **`update_locales.py --tags <tag>`** — exports every locale, then opens an
   auto-PR (`i18n/update_<tag>`, label `i18n`) against `main`.

> **The auto-PR only includes `assets/language/*`.** Its `add-paths` is limited
> to that one directory, so the `ios/Runner/*.lproj/InfoPlist.strings` files the
> script also regenerates are **discarded**. iOS permission strings therefore
> only ever land when someone runs the script locally and commits them
> deliberately. See the trap in §5.

### Manually, whenever you want

This is the path to use when translations arrive between releases — which is
the normal case.

```bash
pip install requests   # once
python3 update_locales.py --api_key "$LOCALISE_EXPORT_API_KEY"
```

Omitting `--tags` exports **all** assets rather than only those tagged for one
release. That is usually what you want for an interim update; just read the
diff before committing, since it refreshes every language at once.

**Prefer the script over Loco's web-UI export.** The script hits
`GET /api/export/locale/<code>.json` with no `format` parameter, which produces
the flat key→value JSON the app parses. Choosing a different shape in the web
UI (structured/nested JSON, or a different charset) produces a file the app
loads without error and reads as empty. If you must export by hand, match the
script's endpoint exactly.

### The HTML legal pages, separately

```bash
python3 update_locales_html.py --api_key "$LOCALISE_EXPORT_API_KEY"
```

This pulls the `license`, `privacy` and `terms` Loco assets into
`assets/html/<prefix>_<lang>.html`, keyed by **language only** (no region).
It is not run by any workflow — always manual.

## 3. Routine: refreshing an existing language

1. Run `update_locales.py` (§2).
2. `git diff --stat assets/language/` and skim the changes.
3. Build the test flavor and switch to the language in Settings.
4. Commit, merge, release.

Nothing else is required — the locale is already registered everywhere.

---

## 4. Checklist: adding a language the app has never shipped

Work through these in order. Steps 1–4 are mandatory; 5–7 are what people
forget.

### 4.1 Confirm the locale code Loco uses

The Loco project's code determines the exported filename, so read it from the
API rather than assuming:

```bash
curl -s -u "$LOCALISE_EXPORT_API_KEY:" https://localise.biz/api/locales \
  | python3 -m json.tool | grep -E '"code"|"name"'
```

`update_locales.py` converts `-` to `_`, so Loco `ar-MA` → `ar_MA.json` and a
bare `ar` → `ar.json`. Both work; they just have to match step 4.3.

### 4.2 Check the translation is complete enough to export

`update_locales.py` **skips any locale at or below 80% translated**
(`MIN_PROGRESS_PERCENTAGE`, and note the comparison is `<=`, so exactly 80%
is skipped). If the new language is below that and you still want it shipped,
add its code to `FORCE_LANGUAGES` at the top of the script:

```python
FORCE_LANGUAGES = ['es_UY', 'vi_VN']
```

Anything in `FORCE_LANGUAGES` is also added to `AUTO_FALLBACK`, meaning
untranslated keys come back filled with the fallback language rather than
empty. Configure the fallback language in Loco itself if English is not what
you want.

### 4.3 Register the locale in Dart

Add the `Locale` to `MyLocalizations.supportedLocales` in
`lib/core/localizations/my_localizations.dart` (the list is alphabetical by
language code):

```dart
Locale('ar', 'MA'),   // must match the exported filename: ar_MA.json
```

This one edit is what makes the language appear in the Settings picker; the
display name and native name come from the `language_picker` package via
`Language.fromIsoCode`, so no name strings are needed.

**Decide where it launches.** If the language should be reviewable in Test
Mosquito Alert before reaching production users, also add it to
`MyLocalizations._betaLocales` (same file) and update
`test/unit/beta_locales_test.dart`. Remove it from that list when the review
comes back clean — that removal *is* the production launch.

**On regional variants.** Register the region the translation was actually done
in — Arabic was translated in Moroccan (`ar_MA`), so the entry is
`Locale('ar', 'MA')` and the file is `ar_MA.json`. This does not restrict the
language to devices set to Morocco: `MyLocalizations.resolveLocale` tries an
exact locale match first and then falls back to matching on language code
alone, so a device set to `ar_EG` or `ar_SA` still resolves to `ar_MA`. Every
Arabic speaker gets the Moroccan file until a second Arabic locale is added —
at which point the picker starts appending country names to disambiguate, the
same way `es_ES` and `es_UY` are shown today.

### 4.4 Export and verify the JSON actually loaded

Run the script, then confirm the file is complete rather than a stub:

```bash
python3 - <<'PY'
import json
en = json.load(open('assets/language/en_US.json'))
new = json.load(open('assets/language/ar_MA.json'))   # <-- your file
print('keys:', len(new), 'of', len(en), '| missing:', len(set(en) - set(new)))
print('empty values:', sum(1 for v in new.values() if not v))
PY
```

A missing key falls back to English at runtime; an **empty string value does
not** — `MyLocalizations.translate` returns `''`, so the UI renders blank.
Empty values are worth chasing before release.

### 4.5 Point the legal-page links at files that exist

Three keys hold *asset paths*, not prose:

| Key | Value shape |
|---|---|
| `privacy_link` | `assets/html/privacy_<lang>.html` |
| `terms_link` | `assets/html/terms_<lang>.html` |
| `lisence_link` | `assets/html/license_<lang>.html` (note the historical typo in the key) |

If the legal pages have **not** been translated, these three keys must resolve
to the English files, exactly as `vi_VN.json` does:

```json
"privacy_link": "assets/html/privacy_en.html"
```

The reliable way to get that is to leave the three keys **untranslated in
Loco** and let `fallback=auto` return the English source value. If a translator
"helpfully" localizes the path to a file that does not exist, the legal-page
WebView opens blank. Verify after every export:

```bash
python3 -c "
import json,os
d=json.load(open('assets/language/ar_MA.json'))
for k in ['privacy_link','terms_link','lisence_link']:
    p=d.get(k,''); print(k, p, 'OK' if os.path.exists(p) else 'MISSING FILE')"
```

If the pages *have* been translated, run `update_locales_html.py` and let the
keys point at the new `_<lang>.html` files. Note those are keyed by **language
only**, so Moroccan Arabic produces `privacy_ar.html`, not `privacy_ar_MA.html`.

### 4.6 Register the language in Xcode (iOS permission prompts)

`update_locales.py` writes `ios/Runner/<lang>-<REGION>.lproj/InfoPlist.strings`,
but **iOS ignores any `.lproj` directory that the Xcode project does not know
about.** Adding the file to disk is not enough.

In Xcode: select the **Runner project** → **Info** tab → **Localizations** →
**+** → pick the language → tick `InfoPlist.strings`. That adds the language to
`knownRegions` and to the `InfoPlist.strings` `PBXVariantGroup` in
`project.pbxproj`.

Verify:

```bash
grep -A30 "knownRegions" ios/Runner.xcodeproj/project.pbxproj   # your language listed?
grep -c "ar-MA" ios/Runner.xcodeproj/project.pbxproj            # should be > 0
```

Skipping this does not break anything visibly — the app's own UI is still
translated, because that comes from `assets/language/`. Only the **system
dialogs** ("Mosquito Alert would like to use your location") stay in English.

### 4.7 Check the backend supports the locale

`my_localizations.dart` carries this note for a reason:

> When adding new languages, please check that the mosquito alert API supports
> the new language. If not, please add it to the API first.

`UserRepository.updateLocale` PATCHes the profile with
`PatchedUserRequestLocaleEnum`. In SDK 0.4.1 that enum is:

```
en es ca eu bn sv de sq el gl hu pt sl it fr bg ro hr mk sr lb nl tr zh-CN
```

Anything absent falls through `orElse: () => PatchedUserRequestLocaleEnum.en`
and is stored server-side as English. **`vi` and `ar` are both missing today**,
so any backend-generated content (including notification text) comes back in
English for those users even though the app UI is translated. Fixing it means
adding the code to the API's locale enum, regenerating the Dart SDK, and
bumping the git ref in `pubspec.yaml`.

### 4.8 Build and check

```bash
fvm flutter build appbundle --release --flavor dev --target lib/main_dev.dart
# or, faster while iterating:
fvm flutter run --flavor dev --target lib/main_dev.dart
```

Then: Settings → language picker → the new language appears with its native
name → strings render → legal pages open → permission prompts (iOS) are
localized.

## 5. Traps worth knowing about

**Hand edits get overwritten.** Any fix made directly in `assets/language/*.json`
must also be entered in Loco, or the next export reverts it — and note that a
**git tag push is enough**, since `update_locales.yml` fires on every tag. Local
corrections that Loco does not yet have are tracked in
[`pending-loco-corrections.md`](pending-loco-corrections.md), which also carries
a pre-export guard script. Check it before exporting.

**The auto-PR drops iOS strings.** As noted in §2, `update_locales.yml` commits
only `assets/language/*`. `ios/Runner/*.lproj/InfoPlist.strings` regenerated by
the same script are thrown away. Commit those manually.

**`vi-VN` is currently unregistered in Xcode.** `ios/Runner/vi-VN.lproj/InfoPlist.strings`
exists on disk but `vi-VN` appears nowhere in `project.pbxproj` and is absent
from `knownRegions`. Vietnamese users on iOS therefore see English permission
dialogs today. Same fix as §4.6.

**`AUTO_FALLBACK` leaks across locales.** In `update_locales.py`, `params` is a
single dict reused for every locale in the loop, and `params['fallback'] = 'auto'`
is set but never cleared. Once any `AUTO_FALLBACK` locale is processed — `ca_ES`
is early alphabetically — every locale after it is exported with `fallback=auto`
too. In practice most locales get auto-fallback regardless of the list. Harmless
in effect (fallback text beats blank text), but the list does not mean what it
appears to mean, so don't reason from it.

**Missing key ≠ empty value.** A key absent from a locale file falls back to
`en_US`. A key present with an empty string renders as empty. Prefer missing
over empty.

**HTML pages are language-only.** `assets/html/` uses `privacy_es.html`, not
`privacy_es_ES.html`, so regional variants share one legal page.

**The bundled Rubik font is unused.** `pubspec.yaml` declares Rubik, but no
`fontFamily` is set anywhere in `lib/`, so the app renders in the platform
default font. That is *convenient* for non-Latin scripts — Bengali, Vietnamese
and Arabic all get proper system fonts with no work — but it does mean the
declared font is dead weight.

## 6. Right-to-left languages

Arabic is the first RTL language in the project. Flutter flips layout
automatically when `Directionality` is RTL, and `GlobalMaterialLocalizations`
(already wired in `lib/app.dart`) supplies the RTL direction for `ar`. Two
things stand in the way:

**The test flavor used to force LTR on the entire app — fixed, keep it that
way.** `lib/app.dart` wrapped the whole widget tree in
`Directionality(textDirection: TextDirection.ltr, ...)` to render the red
"TEST" ribbon in non-production builds. `Localizations` installs the
locale-derived `Directionality` above MaterialApp's `builder`
(`widgets/localizations.dart:744`), so that wrapper sat *below* it and
overrode it: Arabic laid out left-to-right in Test Mosquito Alert, the very
build used to review translations. The ribbon now pins direction through
`Banner`'s own `textDirection` / `layoutDirection` arguments instead, leaving
the subtree's direction alone. Do not reintroduce a `Directionality` in that
builder.

**Direction-agnostic layout has never been needed until now.** A quick audit:

| Pattern | Count | RTL-safe? |
|---|---|---|
| `EdgeInsets.only(left:/right:)` | 4 | no — use `EdgeInsetsDirectional` |
| `EdgeInsetsDirectional` | 0 | — |
| `Alignment.centerLeft` / `topRight` / … | 3 | no — use `AlignmentDirectional` |
| `TextAlign.left` / `.right` | 6 | no — use `.start` / `.end` |
| `Positioned(left:/right:)` | 20 | no — use `PositionedDirectional` |

That is ~33 call sites, most of them in `Positioned` overlays. Everything else
in the app uses `Row`/`Column`/`ListTile`, which flip on their own. So RTL is a
contained piece of work, not a rewrite — but it is real work, and it should be
done and visually reviewed before Arabic is offered in production.
